# v0.1 semantics

`ghaas` compiles a strict manifest into one GitHub Actions workflow per function. The
workflow is the execution boundary: it checks out the target repository, installs a
released ghaas binary, and runs `ghaas runtime invoke <function>`. A workflow run is a
provider record, not a durable ghaas invocation database.

## Manifest

The only supported manifest version is `version: 1`. Unknown YAML fields and multiple
documents are errors. A manifest has `defaults.timeout` and one or more named functions.
Each function supports only:

- `runtime: command`;
- a non-empty `command` argv array;
- an optional positive `timeout`;
- literal `env` values and GitHub Secret `secrets` names;
- an optional `schedule` with required five-field `cron` and IANA `timezone`; and
- an optional `concurrency.max`, whose only supported value is `1`.

`defaults.timeout` applies when a function has no timeout; if both are absent, runtime
and generated job defaults are 15 minutes. Command elements remain separate
operating-system arguments. ghaas does not parse, join, quote, glob, or implicitly
execute them through a shell. Shell behavior must be explicit in the argv, for example
`command: [sh, -c, ./script]`.

Environment names must be valid identifiers. A name cannot be present in both `env` and
`secrets`, and `GHAAS_*` is reserved. At runtime, ambient environment values are replaced
by manifest `env`, then by ghaas-owned `GHAAS_*` metadata. Secret values are injected by
GitHub; they are not read by local validation and are never manifest literals.

## Generated workflow

Generation is deterministic for the same manifest and compiler options. Every generated
file starts with:

```text
# Code generated by ghaas. DO NOT EDIT.
```

The file includes `workflow_dispatch`, an optional schedule and timezone, checkout, the
function timeout, a function concurrency group with `cancel-in-progress: false`, and
`permissions: contents: read`. Its install step selects the Linux amd64 or arm64
`ghaas-v0.1.0` release archive, downloads the matching `SHA256SUMS` entry, verifies it,
and extracts the binary into the runner temp directory before adding it to `GITHUB_PATH`.
The target repository therefore needs no ghaas source tree or Go toolchain; it needs
network access to the pinned release and the runner's standard `curl`, `sha256sum`, and
`tar` tools. The final step is the thin `ghaas runtime invoke <function>` entrypoint.
There are no state, issue, branch-write, retry, lease, or dead-letter steps in v0.1.

The workflow name is exactly `ghaas: <function>`. The generated run-name expression is
exactly:

```yaml
run-name: 'ghaas: <function>/${{ inputs.ghaas_invocation_id || github.run_id }}'
```

GitHub returns that run name as `display_title`; the provider-neutral workflow-run model
exposes it as `DisplayTitle`. For a manual UUID input, the canonical title is exactly
`ghaas: <function>/<uuid>`. An explicit logical-ID query must match that title exactly.
It must not select a run by timestamp, creation order, or “newest” fallback. When
`invoke` omits `--ref`, dispatch uses the target repository's default branch; an explicit
ref overrides it.

Manual invocation IDs are function-scoped as `<function>/<uuid>`; the CLI passes only
the UUID as the dispatch input. A scheduled run has no dispatch ID and uses the
function-scoped `<function>/<github-run-id>` fallback. The provider may delay or omit a
schedule, so a run ID is an identity for an observed run, not a promise that every cron
tick runs.
This run-ID fallback is an explicit v0.1 limitation; deterministic schedule keys and
durable logical invocation state are v0.2 work.

The runtime exports:

```text
GHAAS_FUNCTION
GHAAS_INVOCATION_ID
GHAAS_ATTEMPT
GHAAS_TRIGGER       # manual or schedule
GHAAS_WORKFLOW_RUN_ID
```

`GHAAS_INVOCATION_ID` is an application idempotency key. It correlates attempts; it is
not proof that a command or an external side effect happened exactly once. Use it with
a destination API's idempotency facility, or implement deduplication in the command.
`GHAAS_ATTEMPT` reflects the GitHub Actions run attempt; a normal run is `1` and a rerun may be higher. ghaas does not retry commands in v0.1.

## Scheduling, concurrency, and outcomes

A schedule emits GitHub's cron trigger and, when configured, its IANA timezone. GitHub
controls delivery and start time. Timezone validation does not provide catch-up behavior,
execution windows, or a start-time SLO.

`concurrency.max: 1` emits one per-function GitHub concurrency group and never cancels
an in-progress run. This reduces ordinary overlap but is not a distributed lock and
cannot provide exactly-once execution or effects.

A direct argv command inherits stdout and stderr. A zero exit is successful; a non-zero
exit, cancellation, timeout, missing executable, or other process error is unsuccessful.
GitHub's run status may be unavailable or ambiguous when a runner or network fails.
See [failure model](failure-model.md) for the consequences.

## Roadmap

Durable state, retry scheduling, leases, remote branch persistence, dead-letter or
exhaustion handling, execution windows, SLOs, and additional runtimes are roadmap work.
They are not accepted v0.1 fields or hidden behavior.
